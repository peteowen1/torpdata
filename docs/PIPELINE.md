# torpdata CI pipeline

_Generated by `ops/scripts/pipeline_guide.py` from `docs/pipeline.json`, using runs up to 24 Nov 2026, 12:41pm (Sydney time). Do not edit by hand, except the notes section: rerun the generator._

What torpdata's GitHub Actions do on a match day, in order, and how long each part takes. Two workflows: the Daily Data Release (fetches the new match data from the AFL and uploads it to the torpdata releases, then tells torp to recompute ratings) and, later in the same chain, Build blog data (starts after torp finishes its ratings and predictions, and puts the data the site reads on the R2 store). The ratings and predictions themselves are computed by the torp repository's workflow, described in that repo's guide.

## Daily data release

Workflow: [`daily-data-release.yml`](https://github.com/peteowen1/torpdata/blob/HEAD/.github/workflows/daily-data-release.yml). Median wall time **7 min 06 s** (range 7 min 06 s to 7 min 06 s), from the first job starting to the last job ending, over the 1 run(s) listed below.

One job. It fetches the latest match data from the AFL API and uploads it to the torpdata GitHub releases (chains, play-by-play, player stats, fixtures, results, teams, player details, player game data, derived ratings, injuries). Most runs find nothing new and stop after about two minutes, mainly spent installing R, so they say nothing about a real release and are left out. The guide cannot tell a no-new-data run from a real one except by how it was started, so it counts only manual (Run workflow) runs that took over 5.5 minutes. Among the last 100 successful runs (25 Oct to 25 Nov 2026, the off-season) exactly one released data: the manual run of 26 Oct. So the timings below are ONE run, not a median of five. In the season, scheduled runs that release data will not be counted until the select rule is changed to include them; no-new-data runs that happen to be slow (installing R took up to 17 minutes in some) would then have to be filtered out some other way.

**What starts it, and what it starts:** Started by GitHub's schedule: a run every few hours after games on Thursday to Monday (the times in the workflow file are written as Sydney winter time, AEST, so an hour later in summer) and a daily safety net at 2am AEST; or by hand with Run workflow (force_release skips the new-games check, rebuild_aggregates rebuilds every season since 2021). When it releases data it dispatches the ratings-trigger event to the torp repository, which starts torp's Daily Ratings & Predictions run; that run's timings are in torp's own guide, and its end starts the Build blog data pipeline below.

## Build blog data

Workflow: [`build-blog-data.yml`](https://github.com/peteowen1/torpdata/blob/HEAD/.github/workflows/build-blog-data.yml). Median wall time **7 min 09 s** (range 6 min 48 s to 15 min 48 s), from the first job starting to the last job ending, over the 5 run(s) listed below.

One job. It takes the ratings and predictions that torp has just released, joins them with the match, player and shot data into the parquet files the inthegame-blog site reads (ratings, predictions, game logs, shots, season simulations, team strength and so on), and uploads them to the Cloudflare R2 store under inthegame-data/afl/. All five most recent runs are counted.

**What starts it, and what it starts:** Started by the torp repository's Daily Ratings & Predictions run, whose last step sends the blog-trigger event here; or by hand. It shares its queue (concurrency group daily-release) with the Daily Data Release above, so it waits if a release is running. It starts nothing else: the site reads the files it uploads.

## How to regenerate

```
python C:/dev/ops/scripts/pipeline_guide.py build --repo-dir <this repo>
```

It reads `docs/pipeline.json` (which workflows and jobs are the pipeline, one line per step) and the latest successful runs through `gh`, saves every response raw, and rewrites this file and `docs/pipeline-summary.json`. It fails if the config names a job, step or log pattern that no longer appears, so a renamed step cannot leave a stale description behind. Steps marked **(not confirmed)** were not checked against the script they run.
